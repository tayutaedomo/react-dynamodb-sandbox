# 9. WAF の適用範囲 (Regional vs Global) とルール伝播のタイムラグ

Date: 2026-09-19

## Status
Accepted

## Context
本プロジェクトでは、フロントエンドのホスティング環境として「AWS Amplify Hosting」と「CloudFront + S3」の両方を構築し、またバックエンド API として「API Gateway」を使用している。これらのパブリックなエンドポイントを保護するため、それぞれに AWS WAF (Web Application Firewall) をアタッチし、IP ベースのレートベースルール（100回/5分）によるアクセス制限を実装した。

しかし、WAF の動作確認を行うためのテストスクリプト（連続でリクエストを送信して HTTP 403 Forbidden が返ることを確認するスクリプト）を実行した際、API Gateway と CloudFront (または作成直後の Amplify Hosting) で、**レート制限が実際に機能してアクセスが遮断されるまでの時間** に顕著な違いがあることが判明した。

具体的には、インフラをデプロイした直後にテストを実施すると以下の挙動を示した：
- **API Gateway (Regional WAF)**: スクリプト実行後、即座にブロック (403) された。
- **CloudFront (Global WAF)**: 1000回以上のリクエストを送信しても、数分間はブロックされず (200 OK) アクセスが通ってしまった。

## Decision
この挙動の違いはバグや設定ミスではなく、**AWS のアーキテクチャ設計に起因する仕様**であることをプロジェクトのナレッジとして記録し、今後の E2E テストや運用時の前提知識とする。

### アーキテクチャの根本的な違い
1. **API Gateway (Regional WAF)**
   - WAF は東京リージョン (`ap-northeast-1`) などの単一リージョン内にデプロイされ、API Gateway と同じリージョンで動作する。
   - ルールの作成、変更、アクセスログの集計、およびレート制限の評価が **同一リージョン内で完結** するため、反映が極めて高速である。

2. **CloudFront および Amplify Hosting (Global WAF)**
   - CloudFront (Amplify の裏側も CloudFront が稼働) は世界中の数百の PoP (エッジロケーション) に分散しているため、WAF は `us-east-1` リージョンで Global スコープとして作成・管理される。
   - 作成されたルールは、AWS のグローバルネットワークを介して **世界中のすべてのエッジロケーションに同期 (プロパゲーション)** される。
   - また、レートベースルールのアクセス集計も、エッジごとのトラフィックを収集・合算して評価されるため、タイムラグが生じる。

### 運用上の指針
- **デプロイ直後のテスト待機時間**: Global WAF を CloudFront や Amplify Hosting に新規アタッチ、あるいはルールを変更した直後は、すべてのエッジに設定が行き渡るまで **数分〜最大10分程度の遅延が発生する** ことを許容する。
- **レート制限のすり抜け**: 攻撃の立ち上がりなどにおいて、レートベースルールが集計されて実際に 403 を返し始めるまでにラグがあるため、少量のバーストトラフィックはバックエンドに到達する可能性があることを理解してシステムを設計する。

## Consequences
- インフラ自動化の CI/CD やデプロイ検証スクリプトを構築する際、Global WAF の動作テストには明示的な `sleep` を入れるか、遅延を考慮したリトライロジックを実装する必要がある。
- Regional WAF と Global WAF で、障害対応やルール切り戻しのスピードが異なる点をインシデントレスポンスの計画に組み込むことができるようになった。
