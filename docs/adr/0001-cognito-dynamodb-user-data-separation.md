# ADR 0001: Cognito と DynamoDB におけるユーザー情報の棲み分けとデータ同期

## Status
Accepted

## Context
本プロジェクトでは、認証基盤として AWS Cognito を、アプリケーションのメインデータベースとして Amazon DynamoDB を採用している。
アプリケーションを構築するにあたり、「ユーザー名」や「メールアドレス」といったユーザー情報の正のマスターをどこに置き、どのようにアプリケーション側から参照・検索するかが課題となった。

Cognito は認証（Authentication）に特化したサービスであり、ユーザー情報の保持も可能だが、以下の制約がある。
1. **検索性の低さ**: 「特定のメールドメインを持つユーザー一覧」「ユーザー名での部分一致検索」などのクエリ機能が貧弱である。
2. **パフォーマンスと制限**: バックエンドから Cognito の API を頻繁に呼び出すと、レイテンシが増大し、AWS の API レートリミット（スロットリング）に抵触するリスクがある。
3. **業務データとの結合**: DynamoDB 上に保存される業務データ（例: ユーザーが作成したアイテム等）と JOIN（擬似的な紐付け）を行う際、データソースが分かれていると実装が複雑化する。

## Decision
**Cognito を「認証とセキュリティのマスター（Source of Truth）」とし、DynamoDB を「アプリケーション業務ロジック用のリードレプリカ（コピー）」としてユーザー情報を重複して保持するアーキテクチャ**を採用する。

具体的には以下の設計方針とする。
1. **一意の識別子**: Cognito が発行する `sub` (UUID) を、DynamoDB のユーザーテーブルの Primary Key (Partition Key) として利用する。
2. **データのコピー**: ユーザーのサインアップ時（またはプロフィールの変更時）、Cognito の情報を DynamoDB のユーザーテーブルに同期し、`email` や `username` を重複して保持する。
3. **フロントエンドの表示**: ログイン中の自身の `email` 等を表示するだけの場合は、余計な API 呼び出しを避けるため、Cognito から取得した JWT トークン内の Claim 情報をそのまま利用する。
4. **バックエンドの処理**: 管理画面での検索、バッチ処理、他ユーザーのプロフィール参照などの「業務ロジック」においては、Cognito の API は叩かず、すべて DynamoDB のユーザーテーブルから検索・取得を行う。

## Consequences

### Positive (メリット)
* **スケーラビリティの向上**: アプリケーション内のすべての検索・参照ロジックが高速な DynamoDB だけで完結するため、パフォーマンスが高く、Cognito の API 制限を気にする必要がない。
* **関心の分離**: 認証の複雑な仕組み（パスワード変更、MFAなど）は Cognito に閉じ込め、バックエンドの開発者は DynamoDB の読み書き（業務ロジック）にのみ集中できる。

### Negative (デメリット)
* **データ同期の手間**: Cognito と DynamoDB 間でデータの一貫性（同期）を保つための仕組み（Lambda トリガーなど）を実装・管理するコストが追加で発生する。
