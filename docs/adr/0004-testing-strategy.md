# 4. テスト方針とモックの活用

Date: 2026-09-06
Status: Accepted

## Context (背景と課題)
FastAPI と DynamoDB を用いたバックエンドの API エンドポイントを追加するにあたり、自動テストの導入が不可欠となった。
しかし、自動テスト（CI/CD などを含む）の中で実在する AWS 環境（Cognito や DynamoDB）と直接通信を行うと、テスト用のテーブルやユーザープールを管理するインフラ構築コスト（dynamodb-local コンテナの運用など）や、実行時間の増大、コストの発生が問題となる。

## Decision (決定事項)
バックエンドのテスト戦略として、以下の基準を設ける。

1. **API の単体テスト (正常系中心)**
   * 自動テスト（`pytest`）のスコープとし、高速に実行できるようにする。
   * AWS 依存部分（Cognito の認証検証、DynamoDB への I/O）はすべて `unittest.mock` を用いてモック（ダミー化）する。
   * 例外処理などの異常系は、真に必要なもの（ビジネスロジック上重要なもの）のみに限定し、原則は正常系の検証に留める。
2. **モデル単体テストの省略**
   * PynamoDB のモデル定義そのもの（テーブルや属性の定義）に対する単体テストは、「PynamoDB の挙動をテストしていること」と同義となるため実施しない。
3. **結合テスト（E2E）**
   * 実際のインフラを用いた AWS リソース間の結合テスト（UI から API を叩き、DynamoDB に書き込まれるか等のテスト）は、自動化のコストが高いため、当面は**手動実行による動作確認**で割り切る。

## Consequences (結果)
* **Good**: 外部依存（ネットワーク通信や DB アクセス）が排除されるため、ミリ秒単位で完了する高速な自動テストが実現できる。
* **Good**: インフラ構築コスト（dynamodb-local の用意など）をゼロに抑えることができる。
* **Bad**: モックを利用するため、「PynamoDB のモック」と「実際の DynamoDB の挙動」に乖離があった場合、単体テストをすり抜けて本番環境（手動結合テスト）で初めてエラーが発覚するリスクがある。
