# 2. CognitoとDynamoDB間のユーザーデータ同期戦略

Date: 2026-09-06
Status: Accepted

## Context (背景と課題)
本システムでは、ユーザーの認証管理に AWS Cognito を、プロフィール等のアプリケーションデータの保存に DynamoDB を採用している。
このアーキテクチャにおいて、「Cognito でユーザーが作成された事実」を「DynamoDB のユーザーレコード」とどのように同期・連携させるかが課題となった。

初期案では AWS コマンド等による手動ユーザー作成が想定されていたため、DynamoDB へのレコード作成漏れ（Cognito には存在するが DB には存在しない状態）が発生するリスクがあった。

## Decision (決定事項)
以下の2つのアプローチを組み合わせた**「ハイブリッド同期戦略（フェイルセーフ設計）」**を採用する。

1. **イベント駆動による事前作成 (Post-Confirmation Hook)**
   Cognito のサインアップ確認後 (Post-Confirmation) トリガーに Lambda 関数をアタッチし、ユーザー作成と同時に DynamoDB へ初期レコードを自動登録する。これにより、即座にダウンストリーム処理や管理者画面等からユーザーデータを参照可能にする。
2. **API側の遅延初期化による自己修復 (Lazy Initialization / Fallback)**
   バックエンド API (`/api/me/profile` 等) へのリクエスト時に DynamoDB を確認し、レコードが存在しない場合はその場でデフォルトデータを作成する。
   これにより、万が一 Cognito トリガーが一時的な障害やタイムアウトで失敗した場合でも、ユーザーがログインした段階でシステムが自己修復し、サービス影響をゼロに抑える（Defense in Depth）。

## Consequences (結果)
* **Good**: レコード作成漏れによる予期せぬ API エラー（500 Internal Server Error など）を完全に防ぐことができる。
* **Good**: 堅牢なフェイルセーフ設計となり、本番運用に耐えうる信頼性が確保される。
* **Bad**: ユーザー作成ロジックが「トリガー用 Lambda」と「バックエンド API」の2箇所に分散するため、デフォルト値の仕様変更時には両方のコードを修正する必要がある。
