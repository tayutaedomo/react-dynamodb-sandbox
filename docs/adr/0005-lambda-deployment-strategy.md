# 5. 用途に応じた Lambda デプロイ戦略の使い分け (Docker vs ZIP)

Date: 2026-09-06
Status: Accepted

## Context (背景と課題)
本システムでは AWS Lambda をコンピュートリソースの主軸として利用している。
バックエンド API のように、FastAPI や PynamoDB など多数のサードパーティ依存関係を持つアプリケーションを Lambda にデプロイする場合、標準の ZIP 形式ではパッケージングが複雑になり、OS 依存のネイティブライブラリによる実行時エラー（GLIBC のバージョン違い等）のリスクが高まる。
一方で、Cognito の Post-Confirmation トリガーのような軽量なフック処理に対してまでコンテナイメージ方式を適用すると、ビルド時間や ECR の管理コストがオーバーヘッドとなる。

## Decision (決定事項)
Lambda の役割と依存関係の規模に応じて、以下の2つのデプロイ戦略を明確に使い分ける。

1. **重厚なアプリケーション (バックエンドAPI等)**
   * **方式**: コンテナイメージ方式 (`package_type = "Image"`)
   * **理由**: 複雑な依存関係 (FastAPI, Pydantic, PynamoDB 等) を安全にパッケージングし、ローカルと本番環境の差異をなくすため。
   * **運用**: デプロイ専用スクリプト (`build_and_push.sh`) で ECR に Push した後、Terraform を適用する。

2. **軽量な単一スクリプト (イベントトリガー・フック等)**
   * **方式**: Terraform による ZIP 方式 (`data "archive_file"`)
   * **理由**: 外部ライブラリに依存せず、AWS Lambda Python ランタイムに標準で組み込まれている `boto3` と標準ライブラリのみを使用する前提において、ビルドプロセスを省略して最速でデプロイするため。
   * **運用**: Terraform を `apply` するだけで、差分検知から ZIP 圧縮、アップロードまでを全自動で行う。

## Consequences (結果)
* **Good**: 重厚な API の依存関係地獄をコンテナで解決しつつ、フック処理はインフラ構成ファイルの一部として最速でデプロイできる（適材適所）。
* **Bad**: **（制約事項）** 軽量スクリプト（フック等）にはサードパーティライブラリ（`requests` や `pynamodb` 等）を `import` できない。もし将来的にフック処理が肥大化し外部ライブラリが必要になった場合は、コンテナイメージ方式への移行、あるいは Lambda Layer の導入というアーキテクチャ変更が必要になる。
